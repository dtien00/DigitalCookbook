# Digital Cookbook — Roadmap

Staged plan to evolve the current Vite + React + Supabase scaffold into a Pinterest-style casual recipe hub with bookmarking, likes, and comments.

This roadmap is opinionated about **sequence**, not about exact timelines. Each stage stands alone — finish, ship to yourself, then start the next. Skip ahead only when the prior stage's foundation isn't blocking.

---

## Where We Are Today (baseline)

**Working**: email/password auth (Supabase), recipe CRUD (title, description, cover image, ingredients, steps, servings, public/private), recipe grid with title/description search, profile editing, password change.

**Schema-ready, no UI yet**: `likes`, `favorites` (bookmarks), `comments`, `follows`. The Postgres tables and RLS policies are already in [supabase_migration.sql](./supabase_migration.sql).

**Tech**: React 18 + Vite 5, custom CSS, Supabase (Auth + Postgres + Storage), no TypeScript, no router. See [TECHNICAL_CONCEPTS.md](./TECHNICAL_CONCEPTS.md) for the rationale.

- [x] "My Bookmarks" view. *New `src/components/MyBookmarks.jsx`, linked from the header (Bookmarks button next to Profile). Fetches `favorites` joined to `recipes` ordered by `created_at DESC`. Empty state copy: "No bookmarks yet. Save recipes you love by tapping the bookmark icon on any card."*
- [x] Optimistic UI. *Toggle flips the local `Set` immediately, fires the Supabase write, rolls back if the write fails. No spinner — feels instant.*

**Schema**: technically `favorites` already existed, **but** migration 001 enabled RLS without writing any policies — currently no one can read or write it. Migration 003 (`supabase_migration_003_favorites.sql`) adds:
- Three RLS policies (own-only SELECT / INSERT / DELETE — bookmarks are private to each user)
- A `created_at TIMESTAMPTZ DEFAULT NOW()` column so the My Bookmarks view can sort by recency
- A covering `(user_id, created_at DESC)` index for that query

**Anonymous behavior**: bookmark button is still rendered on cards for anonymous viewers — clicking it opens the Auth view instead of toggling. Pinterest's pattern.

**Exit criteria**: bookmarking from a card persists across reloads; "My Bookmarks" lists everything the user has saved. *Met.*

## Stage 4 — Likes  *(done)*

Goal: lightweight "I appreciate this" signal, separate from bookmarks (Pinterest distinguishes "save to board" from a quick like).

**Tasks**
- [x] New hook for likes. *Done as `src/hooks/useLikes.js` (plural). Bulk-fetches all like rows in a single query, then builds two derived structures: a `Map<recipe_id, count>` for the public counts and a `Set<recipe_id>` for the current user's liked recipes. One query, two outputs — cheaper than two separate fetches.*
- [x] Heart icon with like-count on cards + RecipeDetail. *New `<LikeButton>` component, pill-shaped (heart icon + count number). Three sizes (sm on cards, lg on the detail page). Count rendered only when > 0 to keep zero-state visually quiet. Rose-500 fill when the current user has liked; outline otherwise. Placed top-left on cards (mirroring the bookmark top-right), and inline with the bookmark on the detail page header.*
- [x] Counts strategy. *Chose bulk-fetch-and-aggregate over a Postgres view. At ~50 recipes × low single-digit likes = ~150 rows, this is well under the threshold where a view's compile/maintenance cost pays off. The hook's API is stable — if the data outgrows the bulk-fetch approach, the implementation can swap to a view (or a counter column with trigger) without touching consumers. Captured in `refs/DATABASE_DECISIONS.md` so the decision is explicit.*
- [x] Optimistic UI on toggle. *Same pattern as useFavorites: flip both the userLiked set AND the likeCount map immediately, fire the Supabase write, roll back both on error.*

**Schema**: `likes` already existed, **but** its INSERT policy had a real gap — `WITH CHECK (auth.role() = 'authenticated')` only required the request to be from a logged-in user; nothing stopped a crafted request from inserting a like row claiming to be someone else. Migration 004 replaces it with `WITH CHECK (auth.uid() = user_id)`. Also adds `created_at TIMESTAMPTZ DEFAULT NOW()` for future trending/recently-liked queries (Stage 7) — additive, no read-path changes.

**Anonymous behavior**: like pill renders for anonymous viewers too, with the public count visible and an outline heart. Clicking the heart opens the Auth view (same pattern as bookmarks). The count itself is the social proof that hopefully nudges conversion.

**Exit criteria**: heart toggles, count updates, persists across reloads, scales reasonably on a grid of 30+ recipes. *Met. Toggle is optimistic so the count updates ~0ms; the underlying write completes in the background. The one-query bulk fetch keeps the home grid O(1) Supabase round-trips for likes regardless of card count.*

## Stage 7 — Deferred / Later

Things explicitly *not* in the early roadmap. Each is reasonable, none is urgent.

- **Follows + follow feed**: schema is ready (`follows`), but a useful feed needs more recipes than a solo cookbook generates. Build when the social graph has signal.
- **Discovery / Explore page**: trending recipes, recently-liked, by tag. Worth it once there's a corpus to discover from.
- [x] **Tags filtering UI + tag-aware search**: chip-filter UI + comma-token search syntax. *Done on `stage-7-tags-filter`. App.jsx grows a `parseSearch(raw)` helper that returns `{ mode, tokens }` across four modes — `none` (empty input), `tag` (comma present → split / trim / lowercase / AND-match against tags), `hybrid` (single token with no whitespace → exact tag match OR title/desc substring; covers the common "I typed one word, find it anywhere" case), and `text` (multi-word input → title/desc substring only, since tags are single-word). Whitespace tolerant: `"  italian , pasta  "` parses identically to `"italian,pasta"`. The chip "active" state covers both `tag` and `hybrid` modes so a single-word search visibly highlights the matching tag chip. Above the grid, a chip row lists unique tags from currently loaded recipes sorted by frequency desc with alphabetical tiebreak; collapsed to the top 12 by default with a `+N more` / `Show less` expander to avoid pushing the grid below the fold. Any currently active tag is always pinned into view even when collapsed, so a filter never appears to vanish. Clicking a chip toggles it in the search input via `toggleTagFilter`. Single-tag selection appends a trailing comma (`"italian,"`) so the parser still routes to tag mode (without the comma it would fall to text mode and substring-match titles instead of the tags array). Chip "active" state derives from the parsed input so typed and clicked filters stay in sync. Known limitation: tags only present on unloaded pagination pages won't appear in the chip row until scroll loads them — acceptable at current corpus size. Input placeholder updated to surface the syntax. Ingredient-based search remains out of scope.*
- **Ingredient-based search**: a future direction — type an ingredient and find recipes that use it. Needs a separate query path against the ingredients table; defer until there's a real driver.
- **Realtime updates**: Supabase channels can push new likes/comments live. Nice, not necessary.
- [x] **Private-recipe badge**: visual distinction between public and private recipes. *Done on `stage-7-public-badge`. Originally tracked in `refs/FEATURES.md`; promoted into the roadmap when picked up. Badge renders only when `recipe.is_public === false` (the informative case — public is the default, only private warrants a marker). Lock icon + "Private" label in a `bg-ink/70 text-paper` rounded chip with backdrop blur. Position on cards: `absolute bottom-3 right-3 z-10` over the image gradient overlay (image variant) or body bottom-right (image-less variant) — keeps the top corners free for like / bookmark. On RecipeDetail the badge sits as a centered kicker above the title. Note on visibility: RLS already hides others' private recipes from the grid, so any private card you see is yours by definition — no explicit author check needed. `aria-label="Private recipe"` so screen readers don't read the lock icon glyph as text.*
- [x] **Servings multiplier**: scale ingredient quantities by a stepper (e.g. recipe is for 4, user wants 6 → multiply quantities by 1.5). *Done on `stage-7-servings-multiplier`. Local state only — no schema changes. `targetServings` state in RecipeDetail.jsx initialised from `recipe.servings`; `−`/`+` stepper in the `.recipe-meta` row (paper-shade circular buttons, disabled at 1 / 99 bounds). Multiplier applied via `scaleQuantity(ing.quantity, multiplier)` which rounds to 2 dp and substitutes common fractions (½ ¼ ¾ ⅓ ⅔) for nicer display. A "reset" link appears inline when targetServings ≠ baseServings. Quantities stored as NUMERIC in Postgres so multiplication is clean with no string-parsing.*
- [x] **Ingredient notes**: per-ingredient optional free-text for substitutions and alternatives ("or any neutral oil"; "fresh basil works if you can't find Thai basil") so authors don't have to bake swaps into the ingredient name. *Done on `stage-7-ingredient-notes`. Additive schema (migration 007: `notes TEXT` on `ingredients`, nullable — no RLS changes since the ingredients policies already gate on parent recipe visibility). CreateRecipe.jsx grows a second-row italic input below each ingredient row, persisted in the insert payload as `notes: ing.notes?.trim() || null` (empty strings collapse to NULL so the DB stays clean). Edit-mode hydration includes `notes` in the ingredient fetch. RecipeDetail.jsx renders the note as italic `text-ink/60 font-serif text-sm` sub-text on a new line below each ingredient when present — quiet by design so unflagged ingredients keep the same visual rhythm. Originally tracked in `refs/FEATURES.md`; promoted into the roadmap when picked up (same pattern as the private-recipe badge).*
- [x] **Admin account**: moderation role with the ability to delete any recipe / comment, delete any user, and reset per-recipe likes / bookmarks. *Done on `admin` branch. Migration 008 (`supabase_migration_008_admin.sql`) adds `is_admin BOOLEAN NOT NULL DEFAULT FALSE` on profiles, a `public.is_admin()` helper, additive admin-override DELETE policies on `recipes` / `comments` / `likes` / `favorites` (additive so regular users still control their own content), a BEFORE-UPDATE trigger on profiles that reverts `is_admin` changes by non-admins (prevents self-promotion via the existing own-row UPDATE policy), and two SECURITY DEFINER RPCs: `admin_delete_user(target_id)` which deletes from `auth.users` (cascading through profiles + content) with caller-is-admin + not-self guards, and `bootstrap_admin()` which is a one-shot self-promotion gated by a hardcoded seed-email allowlist (`admin@example.com`) so the seed script can promote the test admin without exposing a general-purpose admin-grant RPC.
