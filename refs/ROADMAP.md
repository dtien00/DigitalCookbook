# Digital Cookbook — Roadmap

Staged plan to evolve the current Vite + React + Supabase scaffold into a Pinterest-style casual recipe hub with bookmarking, likes, and comments.

This roadmap is opinionated about **sequence**, not about exact timelines. Each stage stands alone — finish, ship to yourself, then start the next. Skip ahead only when the prior stage's foundation isn't blocking.

---

## Where We Are Today (baseline)

**Working**: email/password auth (Supabase), recipe CRUD (title, description, cover image, ingredients, steps, servings, public/private), recipe grid with title/description search, profile editing, password change.

**Schema-ready, no UI yet**: `likes`, `favorites` (bookmarks), `comments`, `follows`. The Postgres tables and RLS policies are already in [supabase_migration.sql](./supabase_migration.sql).

**Tech**: React 18 + Vite 5, custom CSS, Supabase (Auth + Postgres + Storage), no TypeScript, no router. See [TECHNICAL_CONCEPTS.md](./TECHNICAL_CONCEPTS.md) for the rationale.

- [x] Optimistic UI. *Toggle flips the local `Set` immediately, fires the Supabase write, rolls back if the write fails. No spinner — feels instant.*

**Schema**: technically `favorites` already existed, **but** migration 001 enabled RLS without writing any policies — currently no one can read or write it. Migration 003 (`supabase_migration_003_favorites.sql`) adds:

- A `created_at TIMESTAMPTZ DEFAULT NOW()` column so the My Bookmarks view can sort by recency

**Anonymous behavior**: bookmark button is still rendered on cards for anonymous viewers — clicking it opens the Auth view instead of toggling. Pinterest's pattern.

**Exit criteria**: bookmarking from a card persists across reloads; "My Bookmarks" lists everything the user has saved. *Met.*

## Stage 4 — Likes  *(done)*

Goal: lightweight "I appreciate this" signal, separate from bookmarks (Pinterest distinguishes "save to board" from a quick like).

**Tasks**
- [x] New hook for likes. *Done as `src/hooks/useLikes.js` (plural). Bulk-fetches all like rows in a single query, then builds two derived structures: a `Map<recipe_id, count>` for the public counts and a `Set<recipe_id>` for the current user's liked recipes. One query, two outputs — cheaper than two separate fetches.*
- [x] Heart icon with like-count on cards + RecipeDetail. *New `<LikeButton>` component, pill-shaped (heart icon + count number). Three sizes (sm on cards, lg on the detail page). Count rendered only when > 0 to keep zero-state visually quiet. Rose-500 fill when the current user has liked; outline otherwise. Placed top-left on cards (mirroring the bookmark top-right), and inline with the bookmark on the detail page header.*
- [x] Counts strategy. *Chose bulk-fetch-and-aggregate over a Postgres view. At ~50 recipes × low single-digit likes = ~150 rows, this is well under the threshold where a view's compile/maintenance cost pays off. The hook's API is stable — if the data outgrows the bulk-fetch approach, the implementation can swap to a view (or a counter column with trigger) without touching consumers. Captured in `refs/DATABASE_DECISIONS.md` so the decision is explicit.*
- [x] Optimistic UI on toggle. *Same pattern as useFavorites: flip both the userLiked set AND the likeCount map immediately, fire the Supabase write, roll back both on error.*

**Schema**: `likes` already existed, **but** its INSERT policy had a real gap — `WITH CHECK (auth.role() = 'authenticated')` only required the request to be from a logged-in user; nothing stopped a crafted request from inserting a like row claiming to be someone else. Migration 004 replaces it with `WITH CHECK (auth.uid() = user_id)`. Also adds `created_at TIMESTAMPTZ DEFAULT NOW()` for future trending/recently-liked queries (Stage 7) — additive, no read-path changes.

**Anonymous behavior**: like pill renders for anonymous viewers too, with the public count visible and an outline heart. Clicking the heart opens the Auth view (same pattern as bookmarks). The count itself is the social proof that hopefully nudges conversion.

**Exit criteria**: heart toggles, count updates, persists across reloads, scales reasonably on a grid of 30+ recipes. *Met. Toggle is optimistic so the count updates ~0ms; the underlying write completes in the background. The one-query bulk fetch keeps the home grid O(1) Supabase round-trips for likes regardless of card count.*

## Stage 7 — Deferred / Later

Things explicitly *not* in the early roadmap. Each is reasonable, none is urgent.

- **Follows + follow feed**: schema is ready (`follows`), but a useful feed needs more recipes than a solo cookbook generates. Build when the social graph has signal.
- **Discovery / Explore page**: trending recipes, recently-liked, by tag. Worth it once there's a corpus to discover from.
- [x] **Tags filtering UI + tag-aware search**: chip-filter UI + comma-token search syntax. *Done on `stage-7-tags-filter`. App.jsx grows a `parseSearch(raw)` helper that returns `{ mode, tokens }` across four modes — `none` (empty input), `tag` (comma present → split / trim / lowercase / AND-match against tags), `hybrid` (single token with no whitespace → exact tag match OR title/desc substring; covers the common "I typed one word, find it anywhere" case), and `text` (multi-word input → title/desc substring only, since tags are single-word). Whitespace tolerant: `"  italian , pasta  "` parses identically to `"italian,pasta"`. The chip "active" state covers both `tag` and `hybrid` modes so a single-word search visibly highlights the matching tag chip. Above the grid, a chip row lists unique tags from currently loaded recipes sorted by frequency desc with alphabetical tiebreak; collapsed to the top 12 by default with a `+N more` / `Show less` expander to avoid pushing the grid below the fold. Any currently active tag is always pinned into view even when collapsed, so a filter never appears to vanish. Clicking a chip toggles it in the search input via `toggleTagFilter`. Single-tag selection appends a trailing comma (`"italian,"`) so the parser still routes to tag mode (without the comma it would fall to text mode and substring-match titles instead of the tags array). Chip "active" state derives from the parsed input so typed and clicked filters stay in sync. Known limitation: tags only present on unloaded pagination pages won't appear in the chip row until scroll loads them — acceptable at current corpus size. Input placeholder updated to surface the syntax. Ingredient-based search remains out of scope.*
- **Ingredient-based search**: a future direction — type an ingredient and find recipes that use it. Needs a separate query path against the ingredients table; defer until there's a real driver.
- **Realtime updates**: Supabase channels can push new likes/comments live. Nice, not necessary.
- [x] **Private-recipe badge**: visual distinction between public and private recipes. *Done on `stage-7-public-badge`. Originally tracked in `refs/FEATURES.md`; promoted into the roadmap when picked up. Badge renders only when `recipe.is_public === false` (the informative case — public is the default, only private warrants a marker). Lock icon + "Private" label in a `bg-ink/70 text-paper` rounded chip with backdrop blur. Position on cards: `absolute bottom-3 right-3 z-10` over the image gradient overlay (image variant) or body bottom-right (image-less variant) — keeps the top corners free for like / bookmark. On RecipeDetail the badge sits as a centered kicker above the title. Note on visibility: RLS already hides others' private recipes from the grid, so any private card you see is yours by definition — no explicit author check needed. `aria-label="Private recipe"` so screen readers don't read the lock icon glyph as text.*
- [x] **Servings multiplier**: scale ingredient quantities by a stepper (e.g. recipe is for 4, user wants 6 → multiply quantities by 1.5). *Done on `stage-7-servings-multiplier`. Local state only — no schema changes. `targetServings` state in RecipeDetail.jsx initialised from `recipe.servings`; `−`/`+` stepper in the `.recipe-meta` row (paper-shade circular buttons, disabled at 1 / 99 bounds). A "reset" link appears inline when targetServings ≠ baseServings. Quantities stored as NUMERIC in Postgres so multiplication is clean with no string-parsing.*
- [x] **Ingredient notes**: per-ingredient optional free-text for substitutions and alternatives ("or any neutral oil"; "fresh basil works if you can't find Thai basil") so authors don't have to bake swaps into the ingredient name. *Done on `stage-7-ingredient-notes`. Additive schema (migration 007: `notes TEXT` on `ingredients`, nullable — no RLS changes since the ingredients policies already gate on parent recipe visibility). CreateRecipe.jsx grows a second-row italic input below each ingredient row, persisted in the insert payload as `notes: ing.notes?.trim() || null` (empty strings collapse to NULL so the DB stays clean). Edit-mode hydration includes `notes` in the ingredient fetch. RecipeDetail.jsx renders the note as italic `text-ink/60 font-serif text-sm` sub-text on a new line below each ingredient when present — quiet by design so unflagged ingredients keep the same visual rhythm. Originally tracked in `refs/FEATURES.md`; promoted into the roadmap when picked up (same pattern as the private-recipe badge).*
- [x] **Admin account**: moderation role with the ability to delete any recipe / comment, delete any user, and reset per-recipe likes / bookmarks. *Done on `admin` branch. Migration 008 (`supabase_migration_008_admin.sql`) adds `is_admin BOOLEAN NOT NULL DEFAULT FALSE` on profiles, a `public.is_admin()` helper, additive admin-override DELETE policies on `recipes` / `comments` / `likes` / `favorites` (additive so regular users still control their own content), a BEFORE-UPDATE trigger on profiles that reverts `is_admin` changes by non-admins (prevents self-promotion via the existing own-row UPDATE policy), and two SECURITY DEFINER RPCs: `admin_delete_user(target_id)` which deletes from `auth.users` (cascading through profiles + content) with caller-is-admin + not-self guards, and `bootstrap_admin()` which is a one-shot self-promotion gated by a hardcoded seed-email allowlist (`admin@example.com`) so the seed script can promote the test admin without exposing a general-purpose admin-grant RPC. **How "Add to shopping list" works (end-to-end):**

1. **Source — RecipeDetail.** [`<SendToShoppingListButton>`](../src/components/SendToShoppingListButton.jsx) reads the recipe's `ingredients` array and the Stage 7 `checkedIngredients: Set<id>`, then filters to *unchecked* ingredients only (`ingredients.filter(ing => !checkedIngredients.has(ing.id))`). 2. **Scale & shape.** Each unchecked ingredient becomes `{ name, unit, quantity, notes }`, where `quantity` is the **raw number** `quantity × servingsMultiplier` (rounded to 2 dp), *not* the `½`/`¼` display string. Storing numbers is what lets the list sum the same ingredient across recipes; the fraction glyphs are re-derived for display only.
3. **Store — useShoppingList (localStorage).** `addItems(items)` folds the batch into the persisted list. Each incoming item is matched against existing rows by a normalized `name + unit` key. On a match: both quantities numeric → summed; otherwise the present one is kept. Notes fill an empty slot but never overwrite (first note wins). No match → appended. Mismatched units of the same name (e.g. `2 cups` vs `200 g`) stay as **separate rows** — there is no unit-conversion table (and no canonical ingredient taxonomy; see Stage 18 edge-case (b)), so the list never invents a wrong total.

- [x] **`addRecipe(recipeId, title, items)` supersedes `addItems(items)`** *(PR #63)* — the send path ([`SendToShoppingListButton`](../src/components/SendToShoppingListButton.jsx)) passes the recipe id + title alongside the ingredient rows. `addRecipe` first **drops any existing sources for that recipeId**, then folds the fresh batch in, so re-sending the same recipe *replaces* its prior contribution instead of stacking a second copy — this also fixes N+2a's known "re-sending sums again" double-count. The merge key is unchanged (normalised `name + unit`); the only difference is that a merge now appends/updates a `Source` on the row rather than summing into an anonymous total.
- [x] **"Recipes in this list" provenance bar** *(PR #64)* — a chip row on [`ShoppingList.jsx`](../src/components/ShoppingList.jsx) between the action buttons and the item list. One `bg-tan-soft text-ink` chip per distinct recipe (derived from the union of all items' sources, ordered by earliest `addedAt`), each showing the recipe title, a `bg-tan` count badge of how many list rows it currently contributes to. (The per-chip `✕` for removal landed with PR #66 — a delete never ships without its undo.) No chip bar when the list is empty. **Hover a chip → highlight its rows**: matching `<li>`s get a `bg-tan/20` tint + a 3px `rust` left-stripe (the FollowingRow bookmark-ribbon idiom in COSMETICS), driven by a `hoveredRecipeId` session-state value. Mouse-hover is not enough on its own — `focus-within` (keyboard) and a tap-to-pin toggle (touch) drive the same highlight.
- [x] **Per-recipe removal with overlap accounting** *(PR #66)* — the chip `✕` deletes **optimistically** — no blocking dialog, matching how single-row removal already works — and fires a rich Undo toast that carries the overlap summary. Hook algorithm: for each item, drop the matching source; if no sources remain → delete the row; else recompute `quantity` from the remaining sources and re-derive the displayed `notes` from the first remaining source that carries one (so deleting the recipe that supplied a note falls back to another's). The toast spells out both buckets — "Removed Coconut rice — jasmine rice removed, coconut milk reduced to 2 cups · Undo" — so a shared ingredient is never *silently* reduced (the exact bug this stage exists to prevent), and the whole deletion is one click to reverse (see the undo tasks below). Decision (2026-06-22): the overlap preview a blocking confirm would have shown moves **into** the toast rather than gating the action — now that deletion is fully reversible, the confirm was redundant friction. *(Supersedes the earlier confirm-dialog sketch.)*
- [x] **Undo for removals ("Recently removed" tray)** *(PR #66)* — the per-row `✕` deletes irreversibly today; make it recoverable. On remove, push the full item (with its `sources`, so a restore is lossless) onto a capped `recentlyRemoved` stack (~last 10) persisted in localStorage beside the list, so an accidental delete survives a reload or tab-close — recovery from human error, not just an in-session convenience. Two affordances: (1) an immediate `toast` with an **Undo** action (react-hot-toast custom JSX, already mounted at root) for the catch-it-now case; (2) a collapsed **"Recently removed (N)"** chip tray below the list — each chip shows the item name + a relative timestamp, a `↩` restore that re-merges it **source-aware** (re-folds into an existing row, or resurrects the contributing recipe's chip if it was the last of its kind), and a `✕` dismiss. "Clear all" empties the tray too (fresh trip, clean slate).
- [x] **Undo covers per-recipe deletion too** *(PR #66)* — the same `recentlyRemoved` stack holds two entry shapes: `{ type: 'item', item }` for a single-row remove, and `{ type: 'recipe', recipeId, recipeTitle, contribution, addedAt }` for a chip `✕`, where `contribution` is a snapshot of that recipe's stripped sources (`[{ name, unit, quantity, notes }]`) — the exact data the deletion already walks, so capturing it costs nothing. **Restore reuses the add path**: undoing a recipe deletion re-runs `addRecipe(recipeId, recipeTitle, contribution)`, which both re-creates the rows the recipe solely owned *and* re-attaches its source to shared rows that were only reduced (coconut milk 2 → 3 cups again, note order restored). Delete and undo are mirror images through the one merge — no bespoke reversal code. Toast/chip copy reflects the multi-item nature ("Removed Coconut rice — 2 items, 1 shared · Undo").

**Edge cases:**
- **Null quantities** ("salt, to taste"): a source may contribute `quantity: null`. Recompute sums only the numerics; if none remain numeric the row keeps `null` and stays listed. A row is dropped only when *all* its sources are gone — never because a sum reached zero.
- **Manual single-row remove** (the existing per-row `✕`): unchanged — drops that one row regardless of provenance (a user override), which just decrements the contributing chips' counts.
- **Mismatched units stay separate rows** (the N+2a rule): unaffected — each `(name+unit)` row owns its own sources, so one recipe can touch several rows independently.
- **Legacy localStorage migration**: rows persisted before this stage have no `sources`. On read, synthesise one `{ recipeId: null, recipeTitle: null, quantity: item.quantity, addedAt: null }` source so they still render and stay individually removable; they group under no chip (or an "Added earlier" catch-all) and aren't per-recipe deletable. Acceptable — lists are short-lived, so the unattributed cohort drains within a session or two.
- **Restore after the source recipe is gone**: an item can linger in the Recently-removed tray after its contributing recipe was deleted via the chip `✕`. Restoring re-adds the item *with its stored sources*, which correctly re-creates that recipe's chip — the item genuinely came from it, so the chip reappearing is right, not a leak.
- **Recipe re-sent before its undo fires**: if you delete Coconut rice, then "Add to shopping list" it again before clicking Undo, the queued recipe-entry is stale. Guard: a recipe-entry whose `recipeId` already has live sources is auto-pruned from the tray, so undo can never double-apply a contribution you already have back.
- **Chip order on restore**: the recipe-entry stores the recipe's original earliest `addedAt`; restore replays it so the undone recipe's chip returns to its prior position in the provenance bar instead of jumping to newest.

**Schema**: none — client-side, localStorage only (same posture as N+2a). Storage key `cookbook.shoppingList` is reused; the stored value stays the items array, now with `sources` on each row.

**Sequence**: lands independently on top of N+2a. Also *unblocks* Stage M+1's "Build shopping list from plan" — that feature needs to attribute the generated list back to the planned recipes, which is precisely the `sources` model defined here.

## Stage 19 - Cooking Mode Timer *(promoted from "Other deferred ideas" — 2026-06-26)*

Goal: cook-along steps that involve waiting ("simmer 20 minutes", "rest the dough 1 hour") get a real kitchen timer. A cook can either start a one-tap **preset timer** authored on the step, or spin up an **ad-hoc timer** for any duration; once running it supports **pause/resume · reset · +1 min**; on expiry it **vibrates and/or chimes**; and the timer is a **floating widget** that survives step navigation and the CookingMode↔RecipeDetail boundary. Extends Stage 15's [CookingMode.jsx](../src/components/CookingMode.jsx).

**Core architectural decision — state lives at App level, not in CookingMode.** The "floating in RecipeDetail *and/or* CookingMode" requirement is load-bearing: a timer must keep running when the cook advances steps, exits cooking mode back to RecipeDetail, or even browses away (pasta doesn't care what tab you're on). `CookingMode` unmounts on exit, so it can't own timer state. State is lifted to App level and shared via a hook, mirroring the Fridge Basket / Shopping List precedent:
- New `src/hooks/useTimers.js` — owns the timer list, localStorage-backed (`cookbook.timers`), same shape as [useFridgeBasket.js](../src/hooks/useFridgeBasket.js) / [useShoppingList.js](../src/hooks/useShoppingList.js).
- New `src/components/TimerWidget.jsx` — a floating overlay rendered once at App level (sibling to `<Toaster>`, the Fridge modal, `<OnboardingTour>`), portaled to `body` at **`z-[120]`** so it floats above CookingMode's `z-[100]` and its ingredient sheet's `z-[110]`.
- `CookingMode` and `RecipeDetail` only *call into* the hook (`startTimer(...)`); neither owns the state.

**Timer mechanics — epoch-based, not interval-decrement.** Decrementing a counter on `setInterval` drifts and freezes under tab-throttling. Each timer is `{ id, label, durationMs, endsAt, remainingMs, status }`. Running: store `endsAt = Date.now() + remainingMs`; a single 250ms ticker recomputes `remainingMs = endsAt - Date.now()` for *display only*. Pause snapshots `remainingMs` and clears `endsAt`; reset restores `durationMs`; +1 min adds 60_000ms. Because `endsAt` is absolute, backgrounding and returning shows the correct remaining time, and localStorage persistence is nearly free (an accidental back-swipe or reload doesn't kill a 20-minute timer).

**Expiry signal.** `navigator.vibrate([...])` (Android-only — iOS Safari ignores it, so vibration is the bonus) plus a WebAudio oscillator beep (no binary asset to ship; cross-platform primary). iOS requires the AudioContext to be unlocked by a user gesture — since every timer is *started by a tap*, resume/prime the AudioContext on `startTimer` so the later chime is permitted. Expired timer flips to a pulsing rose-dark state with a **Stop** button that halts the looping signal; `aria-live="assertive"` announces completion. *Known limitation (documented, not solved in v1):* with the phone screen actually off, mobile throttles timers/audio and the chime may defer until the tab is foregrounded — cooking mode's existing Wake Lock keeps the screen on inside that surface, which mostly sidesteps it; fire-on-visible is the fallback elsewhere; Web Notifications are a future upgrade.

**Phasing:**

| Phase | Schema? | Scope |
|---|---|---|
| **1 — Ad-hoc timer** | none | `useTimers` hook + App-level `<TimerWidget>` + clock button in CookingMode header (and RecipeDetail action cluster) + quick-set sheet (3/5/10/15 min presets + custom `mm:ss`) + WebAudio chime + vibration + pause/reset/+1 controls. Satisfies most of the spec with zero migration. |
| **2 — Per-step presets** | migration 023 (`steps.duration_seconds`) | CreateRecipe per-step optional duration input + edit-mode carry-forward + one-tap "Start N:00" chip on steps in CookingMode (and optionally the RecipeDetail step list). |
| **3 — Polish** | none | drag-to-reposition the widget, sound on/off setting, distinct chime per concurrent timer, multiple-timer stack tuning. |

**Multiple concurrent timers:** the data model is a list from day one (boiling pasta *while* simmering sauce is the common kitchen case), so the widget renders a small stack (~3) of independent pills. Single-timer is the MVP fallback if Phase 1 scope needs bounding, but the list model makes multiple nearly free.

## Stage 21 — Ingredient sections *(promoted from deferred ideas 2026-07-01; gated on Stage 20 §2.1 App.jsx decomposition)*

Goal: "For the sauce" / "For the dough" grouping of ingredients, data-driven (each ingredient carries a nullable `section` label; renderers derive groups from contiguous runs, never from DOM structure). Design sketched 2026-07-01 on the `ingredient-sections` branch. **Do not start until the Stage 20 App.jsx decomposition merges** — this touches CreateRecipe/RecipeDetail/CookingMode and would collide with that refactor.

- [] Migration 024: nullable `section TEXT` on `ingredients` — additive, idempotent, no RLS changes (same shape as migration 007's `notes`). Remember `git add -f`.
- [] `src/lib/ingredientSections.js`: contiguous-run `groupIngredients()` + editor row↔ingredient mapping (`rowsToIngredients()` stamps the nearest-section-above on save; `ingredientsToRows()` reconstructs section rows on edit-load), Vitest specs — mirrors the dragSortCore/shoppingListCore pure-lib convention.
- [] CreateRecipe: heterogeneous row state — an "Add section" control appends a named section row; ingredients inherit the nearest section row above; blank-named section rows drop on save (like blank ingredients). Lift `useDragSort`/`dragSortCore` into the editor so section *and* ingredient rows drag-reorder — closes the editor-reorder loose end above for real. Enter on a section input follows the existing advance contract. No retint — the editor keeps its legacy palette until its deferred retint pass.
- [] RecipeDetail: grouped rendering (heading `<li>`s carry no `data-sort-row`, so drag indexes keep matching the flat array) + per-group collapse via CSS-class hiding (expand-all on drag-start — hidden rows would zero-rect `targetIndexForY`; expand before PDF capture — html2pdf renders screen media; `@media print` force-expand rule). An ingredient dropped across a section boundary adopts the section it lands in (section of the row now above it; at index 0, the row below's). "Save order" persists `section` alongside `order_index`, same row-by-row no-transaction posture.
- [] CookingMode ingredients drawer: same derived headings, no collapse.
- [] Exporters untouched by design — clipboard + shopping-list paths never read `section`, so ingredient provenance and list merging are byte-identical. Per-section export stays rejected (one exporter per recipe; per-section buttons add clutter for a rare edge case).
- [] Living docs in the same change: COSMETICS (section-heading treatment: rust display caps over a tan rule), DATABASE_DECISIONS (migration 024 entry), TESTING (author/reader/print checklist).

**Exit criteria**: a recipe authored with "For the dough" / "For the sauce" sections renders grouped on RecipeDetail (collapsible), in the CookingMode drawer, and in print/PDF; sections survive reload and edit round-trips; dragging an ingredient across a boundary adopts the landing section; recipes without sections and both exports render exactly as today.
